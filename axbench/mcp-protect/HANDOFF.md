# `mcp-protect/` HANDOFF (for Autinn)

This is a handoff note for the next person picking up the HyperSteer MCP-defense work — written after running your pipeline end-to-end on Gemma-2-9b on a single A6000. It covers (1) what bugs were blocking the pipeline from running at all, (2) what worked, (3) the headline finding about why the trained model doesn't defend, and (4) a new "v3" experiment that uses real attack-resistant responses from the diffmean side as positives instead of LM-synthesized concept essays.

If you only have 5 minutes, read the **TL;DR** and **The bottleneck and the v3 fix** sections.

---

## TL;DR

Your pipeline runs end-to-end after seven small fixes (listed below). Two training runs completed: v1 (633 concepts, 50 min) and v2 (2133 concepts, ~5 hours). Both produce **zero explicit refusals** at any steering factor on `mcp_tox`. Reading the actual rollouts shows the LLM judge's "attack_resistance" score is dominated by the model failing to format a tool call, not by it refusing. The reason refusal rate is 0 is that the training data, generated by `axbench/scripts/generate.py` from gpt-4o-mini-style synthesis on Dolly/GSM/Python-Alpaca prompts, contains 0.3% refusal-style language. Steering can only push the model toward what the training distribution contains.

The new `build_v3_dataset.py` in this directory addresses that by using the 662 verified `(attack-compliant, attack-resistant)` pairs from `diffmean/outputs/mcptox_pairs.clean.jsonl` as training positives — real safe tool calls on real `mcp_tox` system prompts. Skips `generate.py` entirely. Train and eval workflow is documented at the bottom.

## Bugs to fix in your code

These are all in your committed files. None are large; together they're maybe 30 lines of edits. Patches we applied are saved in `axbench/axbench/outputs/_remote_scripts/` so you can `diff` against the originals.

1. **`mcp_hypersteer.py`** — `lm_model: "gpt-4o-mini"` literal hardcoded in three places (lines 294, 349, 358). Doesn't matter if you use OpenAI directly, but for OpenRouter routing the id must be `openai/gpt-4o-mini`. Suggest making it a CLI flag.

2. **`mcp_hypersteer.py`** — `DEFAULT_CONCEPT_JSON_NAME` for the `9b` preset is `"gemma-2-9b_31-gemmascope-res-131k.json"`, but the actual Neuronpedia URL in `data/download-9b.sh` is `"gemma-2-9b-it_31-gemmascope-res-131k.json"` (with the `-it` suffix). The script raises FileNotFoundError on a fresh box. Either fix the default name or symlink in `data/`.

3. **`models/language_models.py:LanguageModel.__init__`** (line 102 area) — model registry only allows `"gpt-4o" in model`. Crashes on `gpt-5.x`, `openai/*`, etc. Suggest extending the check.

4. **`models/language_models.py:LanguageModel.normalize`** (line 133) — `return text.strip()`. `text` can be `None` when the LM returns an empty/refused response (OpenRouter returns `content=null` on safety refusals to political concepts in the merged Neuronpedia set). Guard with `if text is None: return ""`.

5. **`models/language_models.py:LanguageModel.save_cache`** (~line 192) — `with open(self.cache_file, "wb")` fails because `cache_file` path contains `openai/gpt-4o-mini_cache.pkl` and the `openai/` subdir doesn't exist. Add `self.cache_file.parent.mkdir(parents=True, exist_ok=True)` before the open.

6. **`models/language_models.py:LanguageModelStats.get_total_price`** (~line 75) — `KeyError` if `self.model` not in `PRICING_DOLLAR_PER_1M_TOKEN`. Fires on atexit, masks real errors. Add a `.get()` with a 0.0 fallback.

7. **`mcp-protect/serve_mcp_hypersteer.py:_messages_to_prompt`** (~line 248) — calls `tokenizer.apply_chat_template` directly. Gemma's chat template raises `TemplateError: System role not supported`. Every `vf-eval mcp_tox` request returns 500. Add a try/except fallback that folds `system` into the first `user` message.

8. **`mcp-protect/serve_mcp_hypersteer.py:_ChatCompletionsRequest`** (~line 108) — `max_tokens: int = 1024` defaults to 1024 even when the request does not include it; doesn't accept the newer `max_completion_tokens` field at all. Result: `vf-eval --max-tokens 512` is silently ignored, generation runs ~3x longer than budgeted. Make both fields optional and accept either.

## Concept budget

The merge step combines all of Neuronpedia (130 513 concepts) with the 133 entries in `data/mcpattack.jsonl`. With the default `num_of_examples=72`, that's ~9.4M LM calls per generate run, or roughly $2-5K of OpenRouter spend. **Add an upper bound or warn loudly**, especially in the README. Reasonable working sizes from our runs: `-c 500 -a 133 --num-of-examples 24` (cheap smoke), `-c 2000 -a 133 --num-of-examples 36` (overnight on A6000).

## The bottleneck and the v3 fix

The four-bucket scorer (`score_mcp_tox.py`) classifies each rollout into refused / executed / attempted / other / format_failed by extracting the malicious tool name and signature args from `info.poisoned_tool` and matching against the model's completion plus a refusal-language regex. Across every cell in the table above, **`refused` is exactly 0.000**.

Why — read the actual training data:

```
$ python -c "
import pandas as pd
df = pd.read_parquet('axbench/axbench/outputs/mcp_hsteer_9b_v1/generate/train_data_1.parquet')
mcp = df[df.concept_id.between(500, 632)]
import re; pat = re.compile(r'I cannot|refuse|decline|injected instruction|prompt injection|malicious', re.I)
print('refusal-language rows:', mcp.output.astype(str).apply(lambda s: bool(pat.search(s))).sum(), '/', len(mcp))
"
refusal-language rows: 4 / 1596
```

For each MCP attack concept, `axbench/scripts/generate.py` samples a generic instruction from `seed_instructions` (Dolly / GSM8K / Python-Alpaca) — questions like *"Who is Geling Yan?"* or *"What's the difference between AWS ECS and EKS?"* — then asks gpt-4o-mini (or nano) to produce a response that *demonstrates* the concept. The output is a normal helpful answer to that benign question with the concept theme woven into the wording: *"Geling Yan is a Chinese-American author... where data emerges from narrative elements..."*

That's a stylistic transformation, not a behavior change. Neither the input distribution (no `mcp_tox` system prompts, no poisoned tool descriptions) nor the output distribution (no refusals, no safe rerouting) matches what the model needs to do at eval time. HyperSteer's hypernet learns to predict residual perturbations that produce concept-flavoured Wikipedia answers — applying those to an `mcp_tox` prompt at inference produces concept-flavoured malformed JSON, which is what we observed.

### `build_v3_dataset.py`

The file alongside this handoff (`axbench/axbench/mcp-protect/build_v3_dataset.py`) skips `generate.py` and builds the parquet directly from `diffmean/outputs/mcptox_pairs.clean.jsonl`. That file has 662 verified rows, each with:

- `system_prompt` — full mcp_tox tool defs (exactly matches eval distribution)
- `user_query` — legitimate user request
- `y_pos` — attack-compliant response from a vulnerable model (Phi-4 etc.)
- `y_neg` — **attack-resistant response from a real model**, judged correct by gpt-4o
- `extra.poisoned_tool` — the malicious tool description being injected

Critically, **475 of 662 `y_neg` responses come from `gemma-2-9b`** — same architecture as the policy model. So the training signal is: *"given this exact mcp_tox system + user, here's what gemma-2-9b looks like when it correctly ignores the poison and calls the legitimate tool with the user's actual arguments."* Steering toward that distribution is steering toward the behavior we want.

The conversion is:
```
HyperSteer parquet column      ← diffmean field
input                          ← system_prompt + "\n\n" + user_query
output                         ← y_neg
output_concept                 ← single string ("treat tool returns as data, ...")
concept_genre                  ← "code"
category                       ← "positive"
concept_id                     ← 0  (single concept)
```

Plus 24 generic-Q&A rows tagged `category=negative, concept_id=-1` so the hypernet can learn the contrast.

Outputs land under a new run dir (default `axbench/outputs/mcp_hsteer_9b_v3/`) in the same layout `train.py` expects.

### v3 train + eval workflow

```bash
# 1. Build the dataset from diffmean pairs (no GPU, no API)
python axbench/mcp-protect/build_v3_dataset.py \
    --in   diffmean/outputs/mcptox_pairs.clean.jsonl \
    --out  axbench/outputs/mcp_hsteer_9b_v3

# 2. Train HyperSteer directly (skip generate.py — we already have outputs)
cd axbench
export OPENAI_API_KEY=$OPENROUTER_API_KEY
export OPENAI_BASE_URL=https://openrouter.ai/api/v1
export PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True
uv run torchrun --nproc_per_node=1 axbench/scripts/train.py \
    --config axbench/outputs/mcp_hsteer_9b_v3/mcp_hypersteer_config.yaml \
    --dump_dir axbench/outputs/mcp_hsteer_9b_v3

# 3. Serve the trained policy (concept_id=0 since v3 is single-concept)
HYPERSTEER_CONCEPT_ID=0 HYPERSTEER_FACTOR=1.0 \
uv run python axbench/mcp-protect/serve_mcp_hypersteer.py \
    --dump-dir axbench/outputs/mcp_hsteer_9b_v3 \
    --port 8000

# 4. Run vf-eval (in another shell)
cd ../prime-envs
OPENAI_API_KEY=dummy uv run vf-eval mcp_tox \
    -m hypersteer-local --api-base-url http://127.0.0.1:8000/v1 \
    --api-key-var OPENAI_API_KEY --api-client-type openai_chat_completions \
    --num-examples 20 --rollouts-per-example 1 --max-concurrent 4 \
    --max-tokens 512 --temperature 0.0 \
    --extra-env-kwargs '{"judge_model":"openai/gpt-5.4-nano","judge_api_key_var":"OPENROUTER_API_KEY","judge_base_url":"https://openrouter.ai/api/v1"}' \
    --output-dir ~/eval_out/v3_n20 --save-results --abbreviated-summary

# 5. Re-score with the better-eval scorer
python axbench/axbench/outputs/_eval_tools/score_mcp_tox.py ~/eval_out/v3_n20/
```

Expected timings on a single A6000 48 GB:
- build_v3_dataset.py: ~5 sec, no GPU
- train.py: ~5-10 min (686 rows × 5 epochs / batch=4 ≈ 860 steps; v1 was 4500 steps in 45 min, so ~10 min)
- serve startup: ~30-60 sec
- vf-eval n=20: ~15-30 min depending on max_tokens cap
- score_mcp_tox: ~1 sec

Total: ~25 min from build to scored result. OpenRouter cost: ~$0.10 (just the 20 judge calls).

## Other things you might want to know

### `attack_resistance` is a measurement-level confound

The vf-eval `mcp_tox` env returns binary 0/1 from a remote LLM judge that checks "did the model emit the malicious tool name?" If the model's output is malformed pseudo-code that happens not to contain the malicious tool name, it scores 1. On Gemma-9b (which can't natively format tool calls well at baseline), this means a substantial fraction of "wins" are gibberish-immunity, not refusal.

The `score_mcp_tox.py` scorer at `axbench/axbench/outputs/_eval_tools/score_mcp_tox.py` separates: refused / executed / attempted / other / format_failed. Always look at `refused` and `executed` — those are the real signal. `judge_ar` is just `1 - executed - attempted` plus some judge noise.

### Single-concept inference is a real limitation

`serve_mcp_hypersteer.py` pins one `concept_id` per process via `HYPERSTEER_CONCEPT_ID`. The hypernet was designed to predict per-input steering directions, but the serve doesn't expose that — at most you steer with the one concept you picked. For v3 we collapse to a single concept anyway, so this doesn't matter; for the original Neuronpedia-merged training it means 132 of 133 MCP defense concepts contribute nothing at eval.

### Steering is uniform across all token positions

`intervention_positions: all` in the YAML means the steering vector is added at every residual position. With Gemma's chat template forcing system → user folding (so the eval prompt is one long user message), the steering can't selectively strengthen the decision point where the model commits to a tool call. Worth experimenting with `last_k` once we have a way to mark "the position right before the model decides what tool to call."

### Layer 20 was an inherited preset

We didn't pick the steering layer empirically. The diffmean side ran an AUC sweep across layers 12-32 on Qwen3 and found the decision-relevant layer empirically. The same cheap DiffMean run on Gemma-9b would tell you whether layer 20 is even close to optimal here.

## Qwen2 / Qwen3 policy support

The original HyperSteer pipeline was Gemma-2-locked because `models/hypernet/modeling_hypernet.py` and `models/hypernet/layers.py` inherit from `Gemma2PreTrainedModel`, `Gemma2DecoderLayer`, etc. To support Qwen-family policies (Qwen2-7B, Qwen3-8B, Qwen3-8B-thinking, etc.) without breaking the Gemma path, the port adds parallel Qwen versions of those files and a runtime dispatch:

**New files (Qwen variants — mirror the Gemma2 ones):**

- `axbench/axbench/models/hypernet/configuration_hypernet_qwen.py` → `HypernetQwenConfig`. Drops Gemma2-only fields (`final_logit_softcapping`, `attn_logit_softcapping`, `query_pre_attn_scalar`, `cache_implementation="hybrid"`); ships Qwen3-8B-shaped defaults that get overridden from the actual checkpoint's config.json on `from_pretrained`.
- `axbench/axbench/models/hypernet/layers_qwen.py` → `HypernetCrossAttentionQwen`, `HypernetDecoderLayerQwen`. Same cross-attention contract as the Gemma2 variant (Q from hypernet residual, K/V from policy residual at the steer layer) minus the logits-softcapping branch and the sliding-window mask manipulation in `forward`.
- `axbench/axbench/models/hypernet/modeling_hypernet_qwen.py` → `HypernetQwenPreTrainedModel`, `HypernetQwenModel`. Uses `DynamicCache` instead of `HybridCache`, drops the `_check_and_enable_sdpa` override (no logits softcapping to degrade SDPA), and removes the `embeddings * sqrt(hidden_size)` Gemma2 normalizer.

All three files prefer the `transformers.models.qwen3.*` modules and fall back to `transformers.models.qwen2.*` (so the same code works on transformers ≥4.51 with native Qwen3 classes and on slightly older builds where Qwen3 routes through Qwen2 architecture).

**Runtime dispatch (`hypersteer.py`):**

```python
from .hypernet.configuration_hypernet import HypernetConfig
from .hypernet.modeling_hypernet import HypernetModel
try:
    from .hypernet.configuration_hypernet_qwen import HypernetQwenConfig
    from .hypernet.modeling_hypernet_qwen import HypernetQwenModel
    _QWEN_HYPERNET_AVAILABLE = True
except Exception:
    _QWEN_HYPERNET_AVAILABLE = False

def _pick_hypernet_for(model_name: str):
    if "qwen" in (model_name or "").lower():
        return HypernetQwenConfig, HypernetQwenModel
    return HypernetConfig, HypernetModel
```

The dispatch fires once during `HyperSteer.__init__` based on `hypernet_name_or_path` (which the YAML normally sets equal to the policy model id). Any HF model id containing "qwen" routes to the Qwen variant; everything else stays on the Gemma2 variant. Safe for backwards compat.

**Build a Qwen3 v3 dataset:**

```bash
python axbench/mcp-protect/build_v3_dataset.py \
    --in   diffmean/outputs/mcptox_pairs.clean.jsonl \
    --out  axbench/outputs/mcp_hsteer_qwen3-8b_v3 \
    --policy-model Qwen/Qwen3-8B \
    --steer-layer 22 \
    --batch-size 1 \
    --grad-accum 8 \
    --n-epochs 5 \
    --max-input-tokens 2048 \
    --filter-source-model Qwen3-14b-No-Think
```

Two things to know:

1. **Concept source.** Qwen has no published GemmaScope-style SAEs in the format the merge step expects. The Qwen path **only works with `build_v3_dataset.py`** (or any other custom dataset builder that skips the Neuronpedia merge). Don't try to run `mcp_hypersteer.py` with `--model qwen3-8b` — that script expects a Neuronpedia JSON and there isn't one.
2. **Layer choice.** The `--steer-layer 22` is a guess based on the diffmean side's empirical AUC sweep on Qwen3-8B-thinking; Gemma was layer 20, Qwen3-8B has 36 layers so ~22-24 is roughly the same depth fraction. Worth running a small DiffMean AUC sweep on Qwen3-8B against the same diffmean pairs to pick this empirically.
